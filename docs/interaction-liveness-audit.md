# 点不动的控件普查（#156）

用户实测报的一条现象——**composer 左下那枚 ＋（悬停提示「添加文件或调用指令」）点了没反应**，
提示气泡出得来（说明 hover 与命中都没问题），点下去什么也不发生——外加一句「这类有些能点的
东西点不了的问题还挺多的」。这份文档是那一轮**一条一条点过去**的普查结果：查到的是什么、
根因在哪一层、怎么处置、证据是什么。

配套的常驻判据是装配实验室的 **F-49 INTERACTION-LIVENESS** 套件（`test/assembly-lab/livenessSuites.ts`）：
它对一批交互点做「点一下 → 1200 毫秒内有没有可观测变化」，把这类问题变成每次改装配都会重跑的断言。

## 一、先说结论：＋ 点不动，根因不在 dsh-one

＋ 的「没反应」**不是禁用态**（按钮的 `disabled` 是 false），也不是被谁盖住，而是：

1. 点下去官方 `ui-input-trigger` 的候选菜单**确实开了**（页面里能看到那个 `div` 被插进
   `conversation.input.overlay`），但**同一瞬间 command 这个 source 的候选拉取失败**；
2. 菜单 reducer 对「这个 source 失败」的处置是**静默摘掉它那一组**，一组不剩时菜单
   **自动关闭**——于是从用户的角度看，就是「点了没反应」（全程唯一的痕迹是**一行
   `console.error`**，藏在 webview 开发者工具里）；
3. 那个失败是：

   ```
   [ui-input-trigger] source "command" candidates failed:
   TypeError: contribution.available is not a function
       at CommandUiRuntime.candidates
   ```

   来源是**官方 `commandUi` 注册表里有一条缺 `available` 的贡献**。官方的
   `CommandContribution` 契约里 `available(session)` 是必填（`dsh-client-ui-commands` 的
   `lib/types/client/contract.d.ts`），官方 `candidates()` 直接 `contribution.available(session)`；
   实测这一轮注册表里是 `[{name:"model", hasAvailable:false}, {name:"file", hasAvailable:true}]`
   ——缺的那条就是 **`@dsh-one/dsh-llm-provider` 注册的 `/model`**（它注册时没给 `available`）。

**正向对照（现场实测，因果闭合）**：在页面里抓官方客户端根 ctx、把那一条贡献从注册表里摘掉，
同一个按钮再点一次——菜单就正常弹出（元素数 3596→3656、弹层 0→1，菜单里是
「添加文件 file / goal / plan / feedback / compact / permission / export」一整套）。
摘之前点一次没反应、摘之后点一次就出来，这就把因果钉在那一条贡献上。

**同一控件在官方 web 页面上也一样点不动**（本轮实测，同一台网关、同一个会话，页面是官方
`/` 而不是我们的装配页）：官方页同样 `contribution.available is not a function`，同样闪一下
就没了。所以这**不是装配（我们的 shell / block list / 沙箱）的问题**，是那条插件贡献违反了
官方契约、而官方 `candidates()` 不防这一手。

**修在哪里**：`@dsh-one/dsh-llm-provider` 是独立仓库（`github.com/imchangchang/dsh-llm-provider`，
装在 `~/.dsh/profiles/web/node_modules/@dsh-one/`），不在本仓库，所以本仓**改不了它的代码**。
已在该仓库立条目（imchangchang/dsh-llm-provider#7），修法是一行：注册那条贡献时按官方契约补上 `available`
（例如 `available: () => true`，或按官方 ui-model-selection 的写法
`available: (session) => sessions.subagentAddress(session.sessionId) === undefined`）。

**人工验收步骤**（用户在 VS Code 里）：

1. 在插件的仓库里补上 `available` 并重新构建/安装，重启 dsh；
2. 打开 dsh-one 的对话面板，把鼠标悬到 composer 左下那枚 ＋ 上（气泡仍应显示
   「添加文件或调用指令」），点一下；
3. **应当看到**：按钮下方弹出一个候选列表（标题「指令」那一组，里面至少有
   「添加文件 file」与宿主提供的各项指令），点菜单外的任意位置可以关掉它；
4. 顺带验同一症状的另一半：在 composer 输入框里打一个 `/`，同样应当弹出这个候选列表
   （今天也是空的——同一根因）。

## 二、普查清单（只列**实测点不动**的；点得动的按 issue 要求不进表）

「在 VS Code 的实际」一栏是**装配页（浏览器验证）里的实测**。VS Code webview 那一整层
（真宿主行为、沙箱）实验室复现不了，凡涉及它的都单独写在「到不了的那一层」里。

| 控件 | 期望 | 在 VS Code 的实际 | 根因层 | 处置 | 证据 |
| --- | --- | --- | --- | --- | --- |
| composer 的 ＋（添加文件或调用指令） | 弹出 `/` 指令候选菜单 | 菜单闪一下即自行关闭，界面上什么也不发生；控制台一行 `candidates failed: TypeError: contribution.available is not a function` | **E（自有插件用错官方机制，把官方那一口整条打挂）** | 修在 `@dsh-one/dsh-llm-provider`（本仓改不了，已立 issue）；本仓加 F-49 常驻钉住（`＋ 不是禁用态`、`没反应时必须留下能指名道姓的失败行`、`摘掉违规贡献后必须恢复`三条） | F-49 的观测：元素数 3596→3596（Δ0）而 DOM 变动 2 次（`div@conversation.input.overlay` 插了又删 = 菜单闪一下）；同一轮官方页同参数 Δ0；摘掉 `model` 后 Δ60 + 弹层 0→1 |
| composer 里打 `/` 触发指令候选 | 同上 | 同上（同一个 source，同一根因） | **E** | 同上（修好插件即恢复） | 同一份注册表读数：`candidates()` 对**每一条**贡献都调 `available`，所以只要有一条不合契约，整批候选（含打字触发的这一路）全废 |

除这两条外，**本轮逐条点过去、没有发现第三条「点不动」**。为了说明「东西点得动」不是抽样
运气，下面把点过的面与读数一并记下（这些不判红，是清单的覆盖面证据）：

| 面 | 点过的控件 | 实测 |
| --- | --- | --- |
| composer | 权限选择（访问模式）、模型选择、上下文用量、发送（空草稿） | 前三个都弹出对应弹层（元素数分别 +29 / +14 / +23，弹层 0→1）；发送在空草稿时是**禁用态**（点它没反应才是对的） |
| 对话区 | 页签「轨迹」/「对话」、会话头右栏开关、助手动作「好的回答 / 有问题的回答 / 在新对话中分支」、消息「复制」、composer dock 的轮次统计与 token 统计 | 全都反应（页签切换元素数 ±2760、右栏开合 ±31、两个 dock 统计各弹一层）。「复制」**DOM 上没有任何变化**，但剪贴板里确实是那条消息的正文（实测读回）——它属于「有作用、看不见」，不是点不动 |
| 侧栏自有树 | 分组过滤胶囊、搜索、折叠/展开全部、添加工作区、设置齿轮、批量选择、回收站入口、清空/恢复全部（计数 0） | 前七个都反应（前三个的读数：+31 / +3 / −29；设置齿轮 DOM 不动但经宿主能力口发出 `dshOne.hostCall`）；后两个在计数 0 时是**禁用态** |
| 设置页各节 | 通用设置 / 插件 / 模型服务 / Agent 预设 / 已归档会话五个导航项、权限预设下拉、语言下拉、字号 +/−、打开配置文件 | 导航项与两个下拉都反应（切节元素数 ±67 上下、下拉弹层 0→1）；打开配置文件经宿主能力口发出 `dshOne.openSettingsDocument`；字号那两枚**当前是禁用态**（减小可用、增大禁用 = 已经到上限） |
| 插件自己的按钮（`@dsh-one/dsh-llm-provider` 的「模型服务」节） | 服务商 / pi-ai 桥接两个页签、每行供应商的 ↗ / ↻ / ✕、＋ 添加供应商 | 全都反应：↻ 与 ✕ 各开一层（元素数 +1）、↗ 走宿主能力口发出一次 `dshOne.hostCall`、＋ 添加供应商展开表单（+26）；已激活的那个页签点了没反应**是正常的**（点当前页签本来就无事发生） |

**没有一条落在 A / B / C / D 四层上**——宿主能力口在本轮涉及的四处（设置齿轮、
打开配置文件、外链 ↗、在访达中打开工作目录）都拿得到回执；webview 沙箱封的原语本轮没有
撞见（外链那条另见 #150 的 F-48）；我们没有盖住或裁掉任何东西（右栏在**折叠态**时内容落在
视口之外，展开后可点——那是折叠的应有形态，不是缺陷）；block list 也没有挡掉任何动作的拥有者
（＋ 的动作拥有者 `ui-commands` / `ui-input-trigger` 都在 chat 树里，实测也真跑到了）。

## 三、到不了的那一层（实验室到不了宿主层，一律写成人工验收）

浏览器验证是普通浏览器 + 假宿主，**VS Code webview 那一整层（真宿主行为、沙箱）它到不了**，
所以下面这几件事本轮**没有验证过**，要人在 VS Code 里看：

- ＋ 修好之后真机那一步（弹菜单、点一项真插进草稿）——步骤见 §一；
- 走宿主能力口的四处（设置齿轮开设置页、打开配置文件、↗ 开系统浏览器、
  在访达中打开工作目录）在真宿主里的**结果**（实验室只验证到「页面发出了这次调用」）；
- 「复制」在真 webview 里的剪贴板写入（实验室里读回是对的，但那是浏览器的剪贴板）。

## 五、这一轮的机器条件（读数复现时要知道）

- 网关是**本机起的隔离实例**（`dsh web --host 127.0.0.1 --port <临时端口> --no-open`），
  实验室只读连它；同一台机器上还有一个用户日常在用的 dsh 实例，它占着约 25 条会话的写句柄。
- **被别的进程占着的会话服务不了**：那种会话打开后只有半个界面（composer 在、会话头不在），
  而且 `command.list` 会回 `command directory warmup failed`（#145 的现场）。所以 F-49 会
  先按「服务得了」挑一条顶层、不在跑、非空的会话当夹具（跳过最新的几条，它们通常正被占着），
  挑不到就如实记事实。这也是为什么本条的读数里会出现「夹具会话 = …」那一行。
- 会话数、工作区数、模型名这些都是**当天数据**，本条的判据一条都不依赖它们：
  点得动/点不动是「前后两次快照的末态差」，官方页那一侧是**同一轮**用同一台网关量的。
