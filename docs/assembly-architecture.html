dsh-one 装配架构：从顶向下

写于 2026-09-20，对应 main 上的 2.0.0 · 本文是 docs/architecture.md 的另一种讲法（那边讲模块与流程、这边讲四层与一次请求怎么走），两边事实一致，细节以那边为准 · slot / shadow / seam / combo 是官方机制的原词，中文只在第一次出现时括注一句

先用一句话说清楚我们在做什么：你的 dsh 网关照常跑，浏览器打开还是完整的官方界面；与此同时，VS Code 里的 dsh-one 页面用同一套官方前端代码渲染出界面——对话区、侧栏、设置页各是一棵「装配树」，装的是官方插件，只是把与 VS Code 容器撞车的官方件挡在门外，再叠上我们自己的件。网关那边一行代码都没改。

0. 三棵树，四个层

「装配」在这个仓库里指：用官方 dsh web 的前端组件，在我们的 shell 里组装出 VS Code 界面。树定义在 src/ui/assembly/trees.ts，一棵树 = 一份 block list（不进这棵树的官方插件）+ 一个自有 frame 插件 + 追加的自有插件。

树落在哪个容器block list自有 frame 插件
CHAT_TREE编辑器标签页（dshOne.assembledChat，单例，可另开会话标签页）2 条：官方外框、官方侧栏@dsh-one/vscode-chat-ui-layout
SIDEBAR_TREE侧栏 view dshOne.chat12 条：官方外框、对话区那几件、设置子页组、侧栏专属件@dsh-one/vscode-sidebar-ui-layout
SETTINGS_TREE编辑器标签页（dshOne.assembledSettings，单例）14 条：官方外框、官方侧栏、对话流卡片组@dsh-one/vscode-settings-ui-layout

浏览器验证（npm run verify:lab）在真网关上跑四棵树：上面三棵生产树，加一棵只存在于实验室的对照档 sidebar-official（同一份 block list、只是不装自有工作区树插件，用来把自有树与官方浏览区逐项对照）。

第 1 层VS Code 扩展宿主（Node） —— 把面板搭起来

你在命令面板点「打开装配」之后（或侧栏/设置被打开时），这一层做六件事：确保网关在跑（没有就启动或复用，绝不碰别人正在用的实例）；用 token 换登录 cookie；带 cookie 请求网关首页，取出官方 __DSH_BOOT__ 清单与前端资产名；按该树的 block list 过滤清单、把自有插件加进去；起 loopback 代理；生成装配页 HTML 塞进 webview。

文件它负责什么
src/ui/assemblyView.ts三个页面的宿主侧：命令与容器、面板生命周期（单例/会话标签页、重载后恢复）、清单与代理的准备、版本门、主题广播、预热
src/server/manager.tsdsh web 进程生命周期：re-own（reload 后认领）、复用探测、spawn、就绪轮询、健康检查、局域网开关
src/server/serverAuth.ts登录凭证：拿一次性 token 换成 cookie，后续请求都靠它证明身份
src/ui/assembly/wireFilter.ts清单过滤：纯函数，输入官方清单与一棵树的 block list，输出「删掉这些、加上自有插件」的新清单，带单测
src/ui/assembly/pageHtml.ts生成装配页 HTML：__DSH_BOOT__、__DSH_TRANSPORT__、__ModuleLoader__ 门面、探针、失败提示条都在这里注入
第 2 层loopback 代理（src/server/assemblyMirror.ts） —— webview 与网关之间的翻译兼保镖

webview 里的页面不能直接连网关：登录 cookie 带不过去，网关还会检查请求来源。所以在 127.0.0.1 上起一个只存在于本机的转发服务器，页面的请求先发给它，由它附上 cookie、把请求来源改写成网关认可的写法，再转给网关。同一窗口同一网关地址只有一个代理实例（引用计数），最后一个面板关掉才消失。

它干的事为什么要这么做
转发普通请求与实时数据流（/api/*、WebSocket 升级）附登录 cookie；Origin / Referer 改写成网关自己的权威；剥掉浏览器自动加的 sec-fetch-*——少任何一步都会被网关的栅栏拒成 403，这是踩过坑后修好的
过滤插件整包（combo）网关把全部插件代码拼成一个大文件并校验内容，改名单重新申请直接 404。所以做法是：整包原样取回来，按每段开头的 window.__ModuleLoader__.load({ 切开，删掉 block list 里的段，拼好再给页面——网关完全不知道这回事
过滤插件事件流（/plugins-local/events）官方前端自己开会拉一条事件流，每帧带的是未过滤的全量插件名单；0.1.6-alpha.2 起客户端会采纳它，不过滤就会把挡掉的官方插件装回来、把我们自己的插件条目卸掉，整页白。所以页面把那条流改道到这里，逐帧跑同一个过滤函数
伺服我们自己的插件产物它们是 dsh-one 自己的代码，不从网关拿，直接读扩展目录下的文件（dist/assembly/plugins/**）
第 3 层webview 页面 —— 官方组件的运行地（注意：不是 iframe，是顶层页面）

这一层几乎全是官方代码在跑：官方的模块加载器接管后建立组件运行环境（cordis 插件树），按清单把插件一个个装起来，我们的 frame 插件注册 root slot 并渲染整页。我们的作品只有那一组自有插件：三个 frame 插件（搭骨架、提供官方要的 layout 服务、把主题落到页面）、主题跟随、会话启动注入与上报、设置齿轮、会话桥，以及工作区树、git 卡片、右键菜单、清空件、会话导出这几件可移植件。

页面上还有一颗诊断探针（只在 VS Code 环境里激活）：把控制台的报错、网络桥的动向转发到 VS Code 的输出面板，方便排查「只在 VS Code 里才出现」的问题。普通浏览器里它完全不启动。另有一条失败提示条：官方渲染器故意让装配错穿出所有边界并卸掉整棵界面，页面运行时发现「起过内容、又连续两拍一个可见的盒都没有」就落一行说明加一个重载入口，页面好着的时候一个字节不动。

第 4 层dsh 网关 —— 你日常在用的那个实例（比如 3080 端口），一行没改

它照常提供四样东西：首页（带 __DSH_BOOT__ 清单与前端资产）、插件整包、普通接口、实时数据流。浏览器直接打开它看到的就是完整官方界面——这就是「双前端」的另一半。

1. 打开一个装配页，依次发生什么

  1. 命令或侧栏被打开，扩展先确认网关活着（没有就按老规矩启动或复用）。
  2. 拿 token 向网关换出登录 cookie。
  3. 带 cookie 请求网关首页，从返回的 HTML 里取出官方清单与前端资产名。
  4. 按这棵树的 block list 过滤清单，把该树的自有插件加进去。
  5. 取共享的 loopback 代理（没有就起一个），生成本地整包 URL——它是过滤版官方整包 + 我们自己的 bundle 的拼接，URL 里的版本号同时代表这两半内容（这是 webview 的缓存键）。
  6. 生成装配页并开面板。
  7. 页面加载：官方 __ModuleLoader__ 门面就位 → 阻塞的 bootstrap 脚本起来 → 主 bundle 按清单装插件（官方插件从代理拿过滤后的整包，我们的插件从本机文件拿）。
  8. 我们的 frame 插件注册 root，界面渲染出来；它声明的那些座（按树而定：对话区的会话面板座与右列座、侧栏位、全宽悬浮层）随之生效，官方那些件照常注册进来。
  9. 官方启动逻辑接着工作：恢复上次的会话，或连上最近的工作区新开一个；要注入某个会话时由我们的会话启动插件把它打开并上报。

2. 发一条消息，数据怎么走

你在输入框打字（官方组件）回车发送
→普通请求
（页面里被改写到代理）
loopback 代理附 cookie、改写好来源头
→
网关收到消息，开始执行这一轮
回复过程中的每一个增量文字片段、工具卡、需要审批的询问
←实时数据流
loopback 代理双向转发，原样不动
←
官方消息流组件边收边渲染，你看着回复逐字出现

整条链路上渲染消息的全是官方代码——我们只是给它换了一个住处的骨架，并把几个不需要的件留在了门外。

3. 怎么验证它没问题（四道）

验证怎么做管什么用
上游探针node scripts/dsh-upstream-watch/probe.mjs（CI 每日自动跑，22 项）官方那些名字还在不在：wire 协议、网关首页的启动契约、整包端点、Origin 栅栏、整包里的 slot / hook / 字段名、本机官方包里的内部标识符。坏了当天就在 issue 里报出来

VS Code 验证scripts/dev-ui-test.sh 起隔离的 VS Code 窗口，人在窗口里操作最终准绳。webview 宿主层才有差异的部分（剪贴板、原生菜单、多 webview 生命周期）只有这里能验
为什么浏览器验证之外还要真机：我们翻过两次车，都是浏览器验证全绿、一进 VS Code 就坏——普通浏览器里页面与转发服务器算「同来源」，问题被掩盖；webview 里算「跨来源」才暴露（一次是传输桥的请求被网关拒绝，一次是浏览器来源声明头被网关误读）。那两条现在都有常驻断言。反过来，探针看不见「名字一个没少、语义变了」这一类：0.1.6-alpha.2 上客户端契约面全绿，可页面整棵渲染不出来（官方把插件名单的下发方式改了），这一类只由实验室抓。

5. 审阅要点：关键取舍与被否掉的备选

我们选了什么为什么当初没选什么、为什么放弃
清单用减法：只列「不要什么」（一树一份 block list）官方升级加新插件我们自动跟上，不必跟着维护长名单；新增条目的理由都写在 wireFilter.ts 的注释里静态白名单（提前挑好要哪些精确版本）：官方一更新我们就滞后，还得跟着维护版本号
在代理上过滤整包（整包取回、删段、拼好再给页面）实测网关校验整包内容，请求里改插件名单会直接被拒（404），所以只能整包拿回再删段改名单重新申请整包：404；给 dsh 配一个只禁用这几个件的专属配置：同一个网关上的官方界面也会跟着坏，违背「官方界面照常能用」的前提
自己写 frame 插件顶替官方外框官方这套组件本来就支持换骨架；把官方外框拿掉后，别的官方件仍要 root 子槽声明、layout 服务与 panelInfo 钩子，这些由我们的 frame 提供「加载官方外框 + 只遮蔽它的 root slot」：实测三条硬约束让它不可行（root 子槽声明是排他的、渲染授权按条目算、服务提供点在同一隔离域唯一），遮蔽后契约全活着但没人渲染，页面还是空白
官方件里能留的都留，只挡两类：与 VS Code 容器撞形态的、这棵树声明不了它槽位的保留官方给用户的能力，只收敛与容器冲突的呈现；槽位声明不了的件留在清单里只是白背一个 id 依赖，摘掉才是对的按「我们用不上」就挡：等于替官方裁剪功能，用户会少掉他自己装的东西
由代理剥掉浏览器自动加的 sec-fetch-*网关会检查来源，而浏览器替我们声明的「我来自另一个站点」会被当成不可信请求拒掉；代理是受网关信任的自己人，转发时去掉这些声明就对了在页面代码里改请求头：浏览器出于安全禁止修改这类头
官方前端代码一律现场从网关取，不打包进扩展版本永远和正在跑的 dsh 一致，扩展安装包也不跟着变大把官方前端打包进 dsh-one：安装包变大，版本一旦错位就出怪问题，每次 dsh 升级还得跟着发新版
整包 URL 里带两半内容的版本号这条 URL 就是 webview 的缓存键（24h 长缓存）：只带官方那半时，我们重建自己的插件 bundle 不改 URL，webview 会一直吃旧缓存，改了界面也看不到只按网关版本做键：就是我们踩过的那次坑；一律禁用缓存：每个新标签页都要重下整个整包
传输用「双通道」：普通请求与数据流分开处理，都指向代理webview 的页面源与网关不同，官方客户端按页面源寻址会打空；我们在页面里提供官方预留的传输 seam，把两条通道显式指向代理让页面与代理同源（浏览器验证时的形态）：webview 里做不到

6. 已知边界

  • 官方 web 侧少几个入口是故意的：编辑器标签页、独立设置页、建目录后接着开会话、编辑器窗口与集成终端这些能力在官方 web 上不存在，那些入口在那儿不渲染——不是漏配。
  • 装配页与官方页同处境，没有 CSP：宿主那层没有 CSP（查过生成页面与 wrapper 的实现），装配页因此也去掉了自带的策略，换来「第三方插件卡片在两边表现一致」；代价是失去脚本注入防护，页面里跑的东西与官方页相同。
  • block 官方外框的代价：root 契约（子槽声明表、layout 服务、主题呈现、panelInfo 钩子）由我们提供，官方改这些得靠实验室的契约套件先炸，而不是用户撞见。
  • 版本门只提示不阻断：装配页期望 dsh 在 [0.1.2-rc.1, 0.2.0) 区间内，区间外只在页面顶部出一条信息条，功能照常可用。
  • 局域网访问默认关闭：开着的时候，同一局域网内拿到带 token 链接的人都能用这台机器上的 dsh（包括跑命令），所以默认不开、状态栏随时可切回本机。
