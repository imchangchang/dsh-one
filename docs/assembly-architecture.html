dsh-one 装配架构：从顶向下

面向接手开发的人 · 生成于 2026-09-14 · 对应验证线 develop/cordis-chat 的 #64 M1 合入态 · 用词遵循 AGENTS.md 词表（装配 / loopback 代理 / 插件整包过滤 / block list / shell 插件 / 双前端 / 浏览器验证 / VS Code 验证）

一句话架构（双前端）：同一个 dsh 网关实例、服务端零改动——官方 dsh web 拿全量插件清单正常使用； dsh-one 在 VS Code webview 里用自有 shell 插件 + 官方对话区组件组装出无侧栏聊天窗口， 不要的插件（官方外框、官方侧栏）由 loopback 代理在转发插件整包时过滤掉。

0. 四层总览

第 1 层VS Code 扩展宿主（Node） — 装配的发起方与代理方
模块职责

第 2 层loopback 代理（127.0.0.1 随机端口，宿主内） — webview 与网关之间的受信中转
路由行为
/api/*反代网关：服务端附 cookie；Origin/Referer 改写为网关权威；剥除 sec-fetch-* 头（否则网关信任栅栏按 Origin 403）
/api/remote.muxWS 升级转发，握手后双向裸管道（流式通道）
/plugins/*反代网关的插件整包（带 cookie）
插件整包过滤拉官方原始整包 → 按 __ModuleLoader__.load({ 起始标记切段 → 删掉 block list 段 → 拼回调养给 webview（网关对整包内容做校验，改名单重拼会 404，只能整包取回后过滤）
/plugins-local伺服自有的 shell 插件 bundle（读盘 dist/assembly/plugins/@dsh-one/vscode-shell/）
默认其余路径透传网关（带 cookie）

安全边界：仅绑 127.0.0.1 随机端口、随面板关闭；页面全程不接触 cookie。

第 4 层dsh 网关（用户日常实例，零改动）

/（index + 清单注入）· /plugins/??…（插件整包，内容校验）· /api/*（REST）· /api/remote.mux（WS 流）· 浏览器信任栅栏（Origin/Referer + Fetch Metadata）· cookie 鉴权（token 换票）。

双前端的另一半：同一实例上，浏览器打开官方 dsh web → 拿原始全量清单 → 完整官方界面照常使用。

1. 启动序列（打开面板时发生什么）

  1. 用户执行 DSH One: Open Assembled Chat → assemblyView 调 manager.ensureStarted()（复用/拉起网关，绝不动外部实例的进程）
  2. serverAuth 用 token 向网关换 cookie（token 取自 dsh 就绪行或 owned record）
  3. 宿主带 cookie GET 网关 / → 从注入 HTML 提取官方 __DSH_BOOT__ 清单原文
  4. wireFilter：剥除 block list 条目 → 追加 shell 插件条目 → 校验（id 唯一 / 批完整）
  5. 起 loopback 代理（127.0.0.1 随机端口）；创建 WebviewPanel，pageHtml 生成 HTML 注入（过滤后清单 + 传输桥 + 探针 + CSP）
  6. 页面加载：queue 门面收编 → 阻塞 bootstrap（client-modules）→ 官方主 bundle 的 WebBoot 接管
  7. WebBoot：建 cordis 根 Context → 种子表（react/cordis/store/slots/primitives，编译进主 bundle）→ 逐插件装载（插件代码经代理：官方段走插件整包过滤，shell 段走 /plugins-local）
  8. 全部插件 active 后 uiRenderer.mount(#root) → React 树：shell 根外框渲染 conversation 槽 → 官方对话区组件接管
  9. 官方启动导航（watchNavigation）：恢复最近会话/连最近工作区 → composer 可用

3. 验证体系（两道验证 + 探针）

两次翻车都是跨源差异：① 同源实验室下 fetch 走相对路径，跨源 webview 才暴露传输桥问题（最终定位为 sec-fetch-* 头被网关信任栅栏 403，已在代理剥除并加 cross-site 等价回归断言）；②「浏览器验证全过 ≠ VS Code 能用」已写进词表与回归断言。
