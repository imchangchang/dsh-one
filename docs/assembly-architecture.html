dsh-one 装配架构：从顶向下

写于 2026-09-14 · 对应验证线 develop/cordis-chat 的 #64 M1 合入态 · 本文里的术语都能在 AGENTS.md 的词表里查到标准说法

先用一句话说清楚我们在做什么：你的 dsh 网关照常跑，浏览器打开还是完整的官方界面；与此同时，VS Code 里的 dsh-one 面板用同一套官方前端代码渲染出一个没有侧栏的聊天窗口。 我们只是把官方界面里两个不适合塞进 VS Code 的插件（官方外框、官方侧栏）在自己这一端过滤掉了，网关那边一行代码都没改。 这就是「双前端」：一个网关，两种界面，各用各的。

架构总图

0. 整个系统就四层

第 1 层VS Code 扩展宿主（Node） —— 负责把面板搭起来

你在命令面板点「打开装配对话区」之后，这一层做四件事：确保网关已经在跑；用 token 换来登录 cookie；向网关要一份官方插件清单，把不要的两个插件从清单里划掉、把我们自己的 shell 插件加进去；最后生成本地转发服务器（loopback 代理）和面板页面，把页面塞进 webview。

文件它负责什么
src/ui/assemblyView.ts命令入口和面板生命周期：什么时候开、什么时候关、关的时候把本地服务器一并收掉
src/server/serverAuth.ts登录凭证：dsh 每次启动会发一个一次性 token，拿它去网关换成 cookie，后续请求都靠这个 cookie 证明身份
src/ui/assembly/wireFilter.ts清单过滤：一份纯函数，输入官方清单，输出「删了两个插件、加了 shell 插件」的新清单，带单测
src/ui/assembly/pageHtml.ts生成装配页的 HTML：官方约定的四个全局对象、安全策略、传输桥、诊断探针都在这里面注入
第 2 层loopback 代理 —— webview 和网关之间的「翻译兼保镖」

webview 里的页面不能直接连网关：登录 cookie 带不过去，网关还会检查请求来源（只有它认的来源才放行）。所以在 127.0.0.1 上起一个只存在于你电脑里的转发服务器：页面的所有请求先发给它，由它代为附上 cookie、把请求来源改写成网关认可的写法，再转给网关；响应原路返回。面板关掉，它就消失。

它干的事为什么要这么做
转发普通接口请求（/api/*）附带登录 cookie；把请求来源（Origin）改写成网关自己；剥掉浏览器自动加的来源声明头（sec-fetch-*）——少了任何一步都会被网关当成可疑请求拒绝（403），这是我们踩过坑后修好的
转发实时数据流（WebSocket）聊天过程中的流式输出、后台任务状态都走这条管道，转发时保持双向原样
过滤插件整包网关把全部插件代码打包成一个大文件下发，还校验文件内容（改名单重新申请会直接 404）。所以我们的做法是：整包原样取回来，按每个插件代码段开头的标记切成一段一段，把 block list 里那两个插件的段删掉，剩下的拼好再给页面——网关完全不知道这回事
伺服我们自己的 shell 插件它是 dsh-one 自己的代码，不从网关拿，直接读扩展目录下的文件
第 3 层webview 页面 —— 官方组件的运行地（注意：不是 iframe，是顶层页面）

这一层几乎全是官方代码在跑。页面加载时，官方主程序（WebBoot）按照清单把插件一个个装起来、建好组件运行环境（cordis 插件树）、最后把界面渲染到页面上。我们唯一的作品是 shell 插件（约 4KB），它做三件官方外框才会做的事：

  1. 搭骨架：官方界面需要一个「根外框」来安放各个区域。我们的根外框只留一个区域——对话区。官方侧栏插件虽然也被加载了，但骨架上没给它留位置，它就没地方出现，这就是「没有侧栏」的实现方式：不是藏起来，是根本没给它留座位。
  2. 补一个最小服务：官方聊天组件硬性依赖一个叫 layout 的服务（管理侧栏/详情面板的开关）。我们提供一个只做必要动作的替代品，官方组件照常工作。
  3. 涂颜色：主题颜色由一个叫 ThemePresenter 的部件写到页面上，它原来住在被过滤掉的官方外框插件里。不过滤它就没有颜色；过滤了它就必须由我们补上——这是我们复刻进 shell 插件的。

页面上还有一颗「诊断探针」（只在 VS Code 环境里激活）：它把控制台的报错、键盘点击事件、网络桥的动向转发到 VS Code 的输出面板，方便排查「只在 VS Code 里才出现」的问题。在普通浏览器里它完全不启动。

第 4 层dsh 网关 —— 你日常在用的那个实例（比如 3080 端口），一行没改

它照常提供四样东西：首页（里面带着官方插件清单）、插件整包、普通接口、实时数据流（WebSocket）。浏览器直接打开它，看到的就是完整的官方界面——这就是「双前端」的另一半。

1. 打开面板时，依次发生什么

  1. 你点「打开装配对话区」，扩展先确认网关活着（没有就按老规矩启动或复用，绝不碰别人正在用的实例）。
  2. 拿 token 向网关换出登录 cookie。
  3. 带 cookie 请求网关首页，从返回的 HTML 里取出官方插件清单。
  4. 过滤清单：删掉官方外框和官方侧栏两个插件，加上我们自己的 shell 插件。
  5. 起 loopback 代理，生成装配页，开面板。
  6. 页面开始加载：先装官方提供的「模块加载器」，再由官方主程序接管。
  7. 官方主程序建组件运行环境，按清单把 44 个插件逐个装起来（插件代码经代理拿：官方插件走过滤后的整包，我们的 shell 插件走本地文件）。
  8. 全部装好后，界面渲染出来：我们的骨架上，官方对话区组件接管主区域。
  9. 官方自带的启动逻辑开始工作：自动恢复你上次聊的会话，或者连上最近用的工作区新开一个——输入框随即可用。

2. 发一条消息，数据怎么走

你在输入框打字（官方组件）回车发送
→普通接口请求
（网络桥转给代理）
loopback 代理附上 cookie、改写好来源头
→
网关收到消息，开始执行这一轮
回复过程中的每一个增量文字片段、工具调用卡、需要审批的询问
←实时数据流
（WebSocket）
loopback 代理双向转发，原样不动
←
官方消息流组件边收边渲染，你看着回复逐字出现

整条链路上渲染消息的全是官方代码——我们只是给它换了一个住处的骨架，并把两个不需要的插件留在了门外。

3. 怎么验证它没问题（两道验证）

验证怎么做管什么用
浏览器验证用 Playwright 开普通浏览器加载同一个装配页，自动跑断言快、自动化，是第一道关：界面渲染对不对、有没有报错、侧栏是不是真的没了、能不能输入发送
VS Code 验证起隔离的 VS Code 窗口真实加载扩展，人在窗口里操作最终准绳。webview 里才有的一些差异（跨来源请求、安全策略执行、焦点行为）只有这里能验
为什么强调两道都要：我们翻过两次车，都是浏览器验证全绿、一进 VS Code 就坏。两次的根子都是同一个——普通浏览器里页面和转发服务器算「同来源」，问题被掩盖；webview 里算「跨来源」，问题才暴露（一次是传输桥的请求被网关拒绝，一次是浏览器来源声明头被网关误读）。所以跨来源环境的回归断言现在常驻在自动化里。

4. 代码都在哪

文件在哪一层一句话说明
src/ui/assemblyView.ts宿主命令入口、面板开关、取清单和过滤的编排
src/ui/assembly/pageHtml.ts宿主（生成页面）装配页的 HTML：四个全局、安全策略、传输桥、探针
src/ui/assembly/wireFilter.ts宿主清单过滤，纯函数，有单测
src/ui/assembly/probe.ts页面诊断探针，只在 VS Code 环境激活
src/ui/assembly/shell/shellPlugin.ts页面（我们的插件）骨架（根外框）、layout 服务替代品、主题着色
src/server/assemblyMirror.ts代理本地转发服务器：接口转发、数据流转发、插件整包过滤、伺服 shell 插件
src/server/serverAuth.ts宿主token 换登录 cookie
dist/assembly/plugins/@dsh-one/vscode-shell/构建产物shell 插件打包后的样子（约 4KB）

5. 审阅要点：六个关键决策，以及当初为什么没有选别的

我们选了什么为什么当初没选什么、为什么放弃
插件清单用减法：只列「不要什么」（block list，目前就两条）dsh 以后升级、加新插件，我们这边自动跟上，不用每次手动维护清单静态白名单（提前挑好要哪些）：dsh 一更新我们就滞后，还得维护二十来个精确版本号；npm 上的版本号和 dsh 自带的也对不齐
在转发服务器上过滤插件整包（整包取回、删掉不要的两段、拼好再给页面）实测发现网关校验整包内容：请求里改插件名单会直接被拒（404），所以只能整包拿回来再删段改名单重新申请整包：404；给 dsh 配一个禁用这两个插件的专属配置：会导致同一个网关上官方界面也打不开，违背「官方界面照常能用」的前提（这是你拍板否掉的）
自己写一个小插件（shell 插件）顶替官方外框官方这套组件本来就支持换骨架；实测把官方外框拿掉后，聊天组件会因为缺一个服务直接报错起不来——所以必须有人顶上，而 VS Code 里能用的骨架只有我们自己写用官方外框但把侧栏藏起来（#60 的老做法）：藏的办法是一堆取巧的补丁，官方界面一更新补丁就可能失效，已废弃
由转发服务器剥掉浏览器自动加的来源声明头（sec-fetch-*）网关会检查来源，而浏览器替我们声明的来源（「我来自另一个网站」）会被网关当成不可信请求直接拒绝。转发服务器是受网关信任的自己人，由它转发时把这些声明去掉就对了在页面代码里改请求头：浏览器出于安全禁止修改这类头；放宽页面安全策略：治标不治本
官方前端代码一律现场从网关取，不打包进扩展版本永远和正在跑的 dsh 一致；扩展安装包几乎不增大（净增约 4KB）把官方前端代码打包进 dsh-one：安装包多 7MB，版本一旦错位就会出怪问题，每次 dsh 升级还得跟着发新版
传输用「双通道」：普通请求和数据流分开处理，都指向转发服务器webview 的页面来源（vscode-webview://）下，官方客户端按默认方式连网关会失败；我们接管这两条线，统一指向转发服务器让页面和转发服务器同源（浏览器验证时的形态）：webview 里做不到

6. 已知边界和接下来的路

  • 侧栏点会话还没接上（M2）：现在在装配面板里开会话靠它自己恢复；下一步做「在 dsh-one 自己的会话列表里点一下，装配面板就打开那个会话」。
  • 主题跟随是半吊子：面板打开时按当前主题定色，之后你在 VS Code 里切主题，它不会实时跟着变（列入 M2）。
  • 面板刷新后要重新打开：VS Code 窗口 reload 后面板不自动恢复（列入 M2）。
  • 更远的两条线：#65 把 dsh-one 特有的功能（git 卡片、会话引用）做成官方格式的插件挂进来；#66 梳理哪些我们自己的组件可以回馈给官方生态。
  • 体积：装配相关让扩展安装包净增约 4KB（就是 shell 插件）；官方前端代码全部现场从网关取。
  • 版本门：如果网关的 dsh 版本和我们测试过的范围不符，页面顶部会出一条提示，功能照常能用。
